📋 Executive Summary

⚠️ Important Finding Critical

The sync system is a custom REST-based offline-first synchronization engine. It is NOT using ElectricSQL for sync — only PGlite for local storage. The system handles bidirectional sync between a React frontend (PGlite/IndexedDB) and an ElysiaJS backend (PostgreSQL).

🔍 Feature Scope

What Exists

✓ Push Sync (Client → Server)

REST batch API /sync/batch with batching, coalescing, dead letter queue, exponential backoff

✓ Pull Sync (Server → Client)

REST API /sync/changes with cursor tracking, auto-pull every 10s

✓ Conflict Resolution

Version-based (Sales) + Timestamp-based (other entities)

✓ syncGroupId Grouping

Groups related parent-child operations (sale + items + payments)

✓ Entity Priority Sorting

Ensures parents before children (sales=1, sale_items=2, etc.)

✓ Dead Letter Queue

Failed operations after MAX_RETRIES (5) go to DLQ

🚨 Code Quality Issues Detected

1. Documentation vs Implementation Mismatch Critical

Location: .claude/skills/avileo-sync/SKILL.md, references/overview.md

Issue: Skills reference ElectricSQL as part of the sync stack, but the actual implementation uses only custom REST-based sync with PGlite

Impact: Developers may expect ElectricSQL sync capabilities that don't exist

2. Sync Hooks Are Gutted, Not Disabled Critical

Location: packages/app/app/lib/sync/registry.ts

Issue: runSyncHooks() always returns { allow: true } — hooks were removed entirely. Skill docs mention createSyncHook() which doesn't exist

Impact: If hooks needed in future, must be reimplemented from scratch

3. Duplicate Entity Priority Maps High

Locations:

  • packages/backend/src/services/sync/framework/OperationSorter.ts:9-20
  • packages/app/app/lib/sync/sync-service.ts:681-692

Issue: Two separate entity priority maps MUST be kept in sync manually when adding entities

Impact: Missing an update causes ordering bugs that are hard to debug

4. 16 Near-Identical Conflict Resolvers High

Location: packages/backend/src/services/sync/framework/ConflictResolver.ts (540 lines)

Issue: Each resolver repeats the same BaseTimestampConflictResolver pattern with minor variations

Impact: ~400 lines of repetitive code, adding new entities = copy-paste existing resolver

5. PuntoVenta Has ConflictResolver But No Handler Medium

Location: ConflictResolver.ts:321-337 (resolver exists)

Issue: PuntoVentaConflictResolver registered but no PuntoVentaSyncHandler in registry

Impact: PuntoVenta entities cannot sync despite having conflict resolution

6. Hardcoded Required Column Defaults Medium

Location: packages/app/app/lib/sync/change-applier.ts:19-29

Issue: REQUIRED_COLUMN_DEFAULTS only covers products and product_variants

Impact: Pull sync may fail for entities with NOT NULL columns missing from payload

7. No Shared Config for Sync Constants Medium

Location: Scattered across config.ts, service-provider.tsx, sync-service.ts

Issue: BATCH_SIZE, SYNC_INTERVAL_MS, MAX_RETRIES defined in multiple places

Impact: Changing sync params requires multiple file updates

🔬 Root Cause Analysis

Why This System Is Complex to Maintain

No Code Generation

Adding an entity requires manually editing ~10 files across both packages

No Shared Config

Entity priorities, sync constants scattered across packages

No Template Enforcement

Handlers are copy-pasted with slight modifications

No Tests

No visible integration test coverage for sync operations

Dead Hook Infrastructure

Hook system was removed rather than completed

The Fundamental Challenge

The system grew organically. Each new entity added:

  • A handler (120-200 lines)
  • A conflict resolver (40-60 lines)
  • Zod schemas
  • Frontend service
  • Type exports in 3+ places
  • Priority entries in 2 places

With 16 entities, this = ~4,000 lines of entity-specific code that must be manually kept in sync.

✅ Recommended Solution

Phase 1: Fix Current Issues (No Framework)

  • Update skill docs — Remove ElectricSQL references
  • Register PuntoVenta handler or remove resolver
  • Extract entity priority to shared package (@avileo/shared)
  • Add missing required column defaults in change-applier.ts

Phase 2: Create Sync Framework (If Worth the Investment)

  1. Create sync-config.yaml defining all entities, priorities, conflict strategies
  2. Create codegen script that generates:
    • Backend handlers from templates
    • Conflict resolvers from strategy
    • Frontend service boilerplate
    • Zod schemas
  3. Move priorities to shared package
  4. Re-implement hooks properly with proper interfaces
  5. Add test utilities

Implementation Steps

1. Create sync-config schema (YAML/JSON)
   - Define: entity name, priority, conflict strategy, hooks

2. Create codegen templates
   - handler.ts.ejs
   - resolver.ts.ejs
   - service.ts.ejs

3. Extract to @avileo/sync package
   - Shared priority config
   - Sync utilities
   - Hook interfaces
   - Codegen CLI

4. Migrate existing entities
   - Run codegen for all 16 entities
   - Delete duplicate files
   - Verify behavior unchanged

5. Add test infrastructure
   - SyncScenario test builder
   - Mock sync operations
   - Conflict scenario simulator

📊 Summary

The sync system is functional but fragile.

Main Challenges

1. Boilerplate explosion

16 entities × multiple files = high maintenance burden

2. Documentation rot

ElectricSQL mentioned but not used

3. Dead infrastructure

Hooks removed rather than fixed

4. Manual synchronization

Priorities, types, configs scattered everywhere

Framework Value Assessment

A framework would help if:

  • More entities will be added (likely)
  • Multiple developers work on sync code
  • Reliability/regression prevention is valued

Otherwise: fixing the immediate issues (docs, PuntoVenta, priorities extraction) is the safer path.
