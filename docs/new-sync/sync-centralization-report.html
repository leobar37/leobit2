Centralizar sin reescribir

Resumen ejecutivo

La arquitectura sirve, pero sus reglas viven en demasiados lugares

El sistema actual sí tiene una base sólida: enqueue en frontend, procesamiento por lotes, handlers en backend, conflictos, reintentos y pull de cambios. El dolor aparece porque los mismos conceptos se repiten en varios archivos, capas y formatos.

Meta: centralización gradual

5+

Infraestructura dormida

Conclusión rápida: Avileo no necesita un sync nuevo. Necesita un framework de definición y coordinación que haga explícitas las reglas compartidas y reduzca la dispersión actual.

Arquitectura actual

Cómo funciona hoy el sync

El sistema opera en dos direcciones: push de cambios locales al servidor y pull de cambios procesados desde el servidor hacia PGlite. La estructura es entendible y relativamente madura.

Push + Pull + Conflicts
Push · frontend Entity Service

Los servicios de entidad escriben localmente y delegan el enqueue vía BaseService.queueSync().

→
Push · cola local SyncService

Encola operaciones, agrupa por syncGroupId, aplica retry, backoff y dead letter.

→
Push · backend SyncEngine

Ordena operaciones, corre validaciones, resuelve conflictos y ejecuta handlers por entidad.

Pull · backend GET /sync/changes

Expone cambios procesados desde packages/backend/src/services/sync/sync.service.ts.

→
Pull · frontend PullService

Descarga cambios paginados y conserva un cursor de sincronización.

→
Aplicación local change-applier

Aplica inserts, updates y deletes a PGlite usando SQL directo.

Punto fuerte Framework parcial ya existente

El backend ya tiene patrón de engine, pipeline, sorter, registry y handlers.

Hallazgos principales

Dónde está el verdadero costo de mantenimiento

Los problemas más caros no son de funcionalidad básica. Son de gobernanza del sync: listas duplicadas, prioridades repetidas, estrategias partidas y piezas buenas que hoy no están activadas como framework real.

Problema central: metadata dispersa

1. Metadata duplicada entre capas

Los mismos conceptos viven en varios sitios y con variantes distintas.

  • packages/app/app/lib/sync/config.ts
  • packages/app/app/lib/sync/sync-service.ts
  • packages/backend/src/services/sync/framework/OperationSorter.ts
  • packages/backend/src/api/sync.ts

2. Infraestructura de hooks subutilizada

El punto de extensión existe, pero la registry está vacía y no está funcionando como capa oficial de reglas pre-sync.

  • packages/app/app/lib/sync/registry.ts:10
  • packages/app/app/lib/services/base-service.ts:163

3. Coordinación push/pull separada

SyncService y PullService funcionan bien, pero su manejo de ciclo de vida no está concentrado detrás de una única fachada.

4. El backend ya es más sólido que el frontend

La parte servidor ya tiene mentalidad de framework. El frontend todavía mezcla coordinación, configuración y política operativa.

Áreas de mejora

Qué debemos mejorar y por qué

Estas mejoras apuntan a reducir fricción futura: menos archivos que tocar, menos reglas escondidas, menos divergencia entre frontend y backend, y una historia más clara para sumar entidades nuevas.

Priorizar bajo riesgo / alto impacto

Fuente única de verdad

Consolidar entidades syncables, prioridades, capacidades y estrategias en un módulo compartido.

Activar la capa de hooks

Usar la registry como punto oficial para reglas de validación previas al enqueue o al envío.

Coordinar push y pull

Introducir una fachada liviana para gobernar ciclo de vida, estado y coordinación de ambos servicios.

Reducir drift de esquema

Endurecer el manejo del schema local para no depender de DDL manual dispersa.

Normalizar políticas

Evitar que estados, conflicto y prioridades sean definidos de forma distinta en cada capa.

Subir el nivel de pruebas

Agregar pruebas de grouped operations, idempotencia, conflict flow y ciclo push→pull.

Principio rector: cualquier mejora debe bajar la cantidad de lugares donde se define la misma regla, sin desarmar el engine actual.

Cómo lo vamos a manejar

Marco propuesto: Sync Definition Framework

En lugar de crear otro motor, proponemos encapsular el existente detrás de un marco de definiciones compartidas, extensiones claras y una coordinación más explícita en frontend.

Formalizar lo que ya funciona

Pilar 1 · Shared Sync Manifest

Un módulo compartido que defina por entidad:

  • nombre canónico
  • prioridad de procesamiento
  • si actualiza sync_status
  • si permite self-heal
  • estrategia de conflicto
  • relaciones parent/child cuando aplique

Pilar 2 · Sync Coordinator

Una fachada en frontend que coordine:

  • inicio y parada de auto-push / auto-pull
  • estado unificado visible para UI
  • gating online/offline
  • invalidaciones y side effects

Pilar 3 · Hook Governance

La registry pasa a ser el lugar oficial para reglas de pre-sync, no solo una utilidad opcional.

Pilar 4 · Definition-driven backend

El backend sigue usando handlers y engine, pero consume definiciones compartidas para ordenar, validar y registrar entidades.

Lo que no vamos a hacer

  • No vamos a reemplazar el engine del backend.
  • No vamos a mover todo a otra tecnología de sync.
  • No vamos a rehacer todos los handlers.
  • No vamos a abrir una migración gigante de una sola vez.

Lo que sí vamos a hacer

  • Consolidar definición.
  • Centralizar gobierno de reglas.
  • Reducir duplicación de política.
  • Mejorar extensibilidad con riesgo controlado.
Plan propuesto

Plan incremental para ordenar el sync

El plan está pensado para capturar el mayor valor primero. Las primeras fases tienen poco riesgo técnico y alto impacto sobre mantenibilidad y claridad operativa.

Orden recomendado: 1 → 5
F1

Extraer definiciones compartidas

Crear una sola fuente de verdad para entidades, prioridades, capacidades y estrategias base.

  • Mayor impacto con menor riesgo
  • Reduce drift inmediato
F2

Activar hooks

Convertir la registry en capa real de gobierno para reglas previas al sync.

  • Empezar con 1 o 2 entidades críticas
  • Medir valor antes de expandir
F3

Agregar Sync Coordinator

Unificar el ciclo de vida de push/pull sin tocar la lógica interna de procesamiento.

F4

Endurecer schema y constantes

Reducir SQL manual y centralizar estados / estrategias donde corresponda.

F5

Revisar fuente del pull

Evaluar si conviene mantener el acoplamiento actual al audit log o desacoplarlo más.

Fase Objetivo Resultado esperado Riesgo
F1 Eliminar definiciones repetidas Agregar o cambiar una entidad será un cambio localizado y predecible Bajo
F2 Dar sede oficial a reglas pre-sync Menos lógica escondida dentro de servicios o handlers Bajo
F3 Unificar coordinación frontend Manejo más claro de auto-sync, pull, estado y efectos colaterales Bajo / Medio
F4 Reducir drift de schema y estados Menor divergencia entre definición compartida y persistencia local Medio
F5 Revisar coupling del pull Mejor claridad del source of truth de cambios servidos al cliente Medio
Riesgos

Qué pasa si no ordenamos esto ahora

El sistema puede seguir funcionando, pero cada nueva entidad o cambio de política hará crecer el costo oculto.

Costo diferido = deuda operativa

Riesgo de drift

Las mismas reglas pueden divergir entre frontend y backend sin que sea obvio en revisión.

Riesgo de onboarding lento

Entender dónde tocar el sync seguirá siendo más caro para cualquiera que entre al módulo.

Riesgo de features lentas

Cada entidad nueva implicará revisar múltiples listas, mapas, unions y reglas repetidas.

Riesgo más importante: no es una caída inmediata del sistema, sino una pérdida sostenida de velocidad y confianza al extender el sync.

Conclusión

El plan correcto es ordenar, no reconstruir

El sistema actual ya contiene piezas valiosas. La oportunidad está en volver explícitas sus definiciones y darles una sede única para que el sync deje de sentirse repartido.

North star: definición compartida

Decisión final recomendada

Construir un Sync Definition Framework sobre la arquitectura existente, empezando por shared definitions y hook governance.

Mensaje operativo

Primero consolidamos definiciones, luego coordinación, y recién después tocamos temas más sensibles como el source del pull.

En una frase: Avileo no necesita otro sistema de sync; necesita que el suyo tenga una columna vertebral compartida y explícita.
