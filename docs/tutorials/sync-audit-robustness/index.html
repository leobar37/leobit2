Hallazgo Principal

El archivo sync-service.ts es un monolito de 44KB y 1120+ lineas que combina 6 responsabilidades distintas. Tiene cero tests unitarios. Este es el riesgo mas critico: el componente mas grande y complejo del sistema de sync no se puede testear.

Push: Client → Server

  1. Componente escribe en PGlite local
  2. BaseService.queueSync() encola operacion
  3. SyncService.enqueue() aplica coalescing
  4. Auto-sync cada 5s procesa pendientes
  5. POST /sync/batch al backend
  6. Backend: validate → conflict check → execute

Pull: Server → Client

  1. Auto-pull cada 10s consulta cambios
  2. GET /sync/changes?since=cursor
  3. Backend filtra por businessId + timestamp
  4. change-applier.ts aplica a PGlite
  5. Cursor persiste en localStorage
  6. TanStack Query invalida cache para refrescar UI

Bugs Criticos

Riesgo inmediato de errores en produccion. Cada uno incluye evidencia, impacto y sustento.

C1

SyncService es un monolito de 44KB (1120+ lineas)

Archivo: packages/app/app/lib/sync/sync-service.ts

Por que es peligroso: Combina 6 responsabilidades: gestion de cola, procesamiento, HTTP client, dead letter queue, resolucion de conflictos, e inicializacion SQL schema. Cualquier cambio tiene riesgo de regresion en funcionalidad no relacionada.

Produccion: Un bug en dead letter puede afectar el enqueue. Un error en initTables puede impedir toda la sincronizacion. No hay forma de testear estas responsabilidades de forma aislada.

Evidencia: 0 archivos de test para el modulo mas grande del sistema de sync.

Ver codigo problematico 
// Constructor con init async fire-and-forget
constructor(pg: PGlite, businessId: string, authToken: string) {
  this.pg = pg;
  this.businessId = businessId;
  this.authToken = authToken;
  void this.initTables(); // PROBLEMA: no se espera
}

// HTTP directo sin abstraccion
private async sendBatchToServer(operations) {
  const apiUrl = import.meta.env.VITE_API_URL || "http://localhost:5201";
  const response = await fetch(`${apiUrl}/sync/batch`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${this.authToken}`,
      "x-business-id": this.businessId,
    },
    body: JSON.stringify({ operations: ... }),
  });
  // parseo manual de respuesta...
}
C2

PullService: codigo duplicado divergente

Archivo: packages/app/app/lib/sync/pull-service.ts

Por que es peligroso: pull() y pullWithOptions() comparten ~80% de logica pero estan implementados como metodos separados. Ya divergieron: pullWithOptions() NO incrementa consecutiveFailures ni actualiza backoff en errores HTTP.

Produccion: Bugs corregidos en pull() no se aplican automaticamente en pullWithOptions(). El staged loading (que usa pullWithOptions) tiene manejo de errores debilitado.

Ver divergencia 
// pull() - SI incrementa failures
if (!response.ok) {
  this.consecutiveFailures++;      // OK
  this.currentBackoff = this.getBackoffDelay();
  this.lastError = `Pull failed: ${response.status}`;
}

// pullWithOptions() - NO incrementa failures
if (!response.ok) {
  const errorText = await response.text();
  return {
    success: false,
    // consecutiveFailures NO se incrementa
    // backoff NO se actualiza
    error: `Pull failed: ${response.status} ${errorText}`,
  };
}
C3

Superficie de SQL injection en change-applier.ts

Archivo: packages/app/app/lib/sync/change-applier.ts

Por que es peligroso: Los nombres de columna vienen del payload del servidor via toSnakeCase(change.payload). filterValidColumns usa lista negra (elimina columnas malas conocidas), no lista blanca (solo permite columnas validas). Si el backend envia campos inesperados, se intentan insertar como columnas.

Produccion: Errores SQL silenciosos al insertar columnas que no existen, o peor, escribir en columnas que no deberian modificarse.

Ver codigo vulnerable 
// Columnas del payload van directo al SQL
const snakeCaseData = toSnakeCase(change.payload); // sin whitelist
const data = filterValidColumns(tableName, snakeCaseData); // solo blacklist

const insertSql = `
  INSERT INTO "${tableName}" (${columns.map(c => `"${c}"`).join(", ")})
  VALUES (${columns.map((_, i) => `$${i + 1}`).join(", ")})
`;
// columns viene de Object.keys(data) -> derivado del payload
C4

initTables() fire-and-forget en constructor

Por que es peligroso: El constructor llama void this.initTables() sin esperar. Cualquier llamada a enqueue() o processPending() ANTES de que las tablas existan falla con error SQL.

Produccion: En dispositivos lentos con PGlite en cold start, la primera operacion de sync falla. El usuario ve "error de sincronizacion" sin explicacion clara.

Ver solucion propuesta 
// SOLUCION: Lifecycle guard con Promise
private ready: Promise<void>;

constructor(pg: PGlite, businessId: string, authToken: string) {
  this.pg = pg;
  this.businessId = businessId;
  this.authToken = authToken;
  this.ready = this.initTables(); // guardar Promise
}

async enqueue(params: EnqueueParams): Promise<string> {
  await this.ready; // esperar inicializacion
  // ... resto del codigo
}
C5

No hay cleanup al cerrar sesion o cambiar negocio

Por que es peligroso: ServicesProvider solo llama coordinator.stop(). La cola sync_operations, dead letter, cursor en localStorage, y cache TanStack Query NO se limpian. Si el usuario pertenece a multiples negocios, los datos del negocio anterior persisten.

Produccion: Operaciones del negocio A pueden enviarse con token del negocio B. Violacion de multi-tenancy. Datos de clientes/ventas cruzados entre negocios hasta que pull los sobrescribe.

Problemas de Alta Prioridad

No causan fallas inmediatas pero degradan robustez y rendimiento.

H1

Polling cada 5s para estado de sync

SyncStateProvider ejecuta syncService.getStatus() cada 5 segundos, consultando PGlite. Incluso cuando el sistema esta idle. Multiplicado por los intervalos de push (5s) y pull (10s), son ~3 consultas cada 10s sin actividad. Un enfoque event-driven eliminaria esta carga innecesaria en dispositivos moviles.

H2

Backoff duplicado entre SyncService y PullService

Ambos mantienen su propio consecutiveFailures y currentBackoff. backoff.ts provee calculateBackoffDelay() pero SyncService reimplementa la formula inline. Son identicas hoy, pero la duplicacion garantiza que divergeran.

H3

SyncCoordinator vacio (23 lineas)

Solo tiene start(), stop(), getCombinedStatus(), forceSync(). No coordina: no previene pull durante push, no reacciona a eventos de red, no gestiona el ciclo de vida conjunto. Deberia ser el orquestador central pero es un passthrough.

H4

applyUpdate salta registros no-existentes sin error

Cuando un update llega para un registro que no existe localmente, retorna {success: true} sin hacer nada. El servidor cree que el cambio fue aplicado, pero el cliente nunca lo reflejo. Inconsistencia de datos invisible.

Ver codigo 
if (existingResult.rows.length === 0) {
  console.warn("Update for non-existent record skipped");
  return { success: true }; // Retorna exito sin hacer nada!
}
H5

Codigo muerto en PullService.pull()

El bloque if (changes.length === 0) return { success: true, changesApplied: 0, hasMore: false } aparece dos veces en el mismo metodo (lineas ~145 y ~170). El segundo es inalcanzable porque el primero ya retorna.

H6

Zero tests para SyncService (push)

El modulo mas grande y complejo (44KB, enqueue, coalescing, dead letter, self-heal, conflicts) no tiene tests unitarios. Los tests existentes cubren pull-service, change-applier, staged-pull-coordinator, backoff y schema-mapper, pero NO el push.

Oportunidades de Abstraccion

Cada extraccion resuelve un problema especifico de testabilidad o mantenibilidad.

1. Extraer ISyncQueue

Por que: La gestion de la cola (enqueue, coalescing, mark status) es cohesiva y testeable independientemente del HTTP client. Habilita: Tests unitarios del coalescing (create+update=merge, create+delete=cancel), dead letter flow, y self-heal sin mockear fetch.

Ver interfaz propuesta 
export interface ISyncQueue {
  enqueue(params: EnqueueParams): Promise<string>;
  getPending(limit: number): Promise<SyncOperationRecord[]>;
  markProcessing(id: string): Promise<void>;
  markCompleted(id: string): Promise<void>;
  markFailed(id: string, error: string): Promise<void>;
  moveToDeadLetter(id: string, error: string): Promise<void>;
  getStatus(): Promise<SyncStatus>;
}

2. Extraer ISyncHttpClient

Por que: SyncService y PullService usan fetch() directamente con headers manuales. Una capa comun elimina duplicacion y permite mockear la red. Habilita: Tests de procesamiento sin network, retry centralizado, consistencia en auth headers.

Ver interfaz propuesta 
export interface ISyncHttpClient {
  sendBatch(ops: SyncOperationRecord[]): Promise<BatchSyncResponse>;
  fetchChanges(opts: {
    since?: string;
    limit?: number;
    entityTypes?: string[];
  }): Promise<PullResponse>;
}

3. Unificar pull() + pullWithOptions()

Por que: ~80% de logica duplicada. La divergencia actual ya causo un bug (backoff no se aplica en pullWithOptions). Habilita: Un solo path de codigo que mantener, fixes aplican a ambos flujos.

Ver refactor 
// ANTES: dos metodos separados
async pull(): Promise<PullResult> { /* 80 lineas */ }
async pullWithOptions(opts): Promise<PullResult> { /* 90 lineas */ }

// DESPUES: un metodo unificado
async pull(options: PullOptions = {}): Promise<PullResult> {
  const cursor = options.since ?? this.loadCursor(options.cursorKey);
  const entityTypes = options.entityTypes;
  // ... logica comun
}

4. Event-driven status updates

Por que: Reemplazar polling de 5s con EventTarget. SyncService emite evento al cambiar estado. SyncStateProvider escucha eventos en vez de consultar BD. Habilita: Actualizaciones instantaneas de UI, menos carga en IndexedDB, base para notificaciones.

Estrategia de Testing Recomendada

1
Unitarios de ISyncQueue: Coalescing logic, dead letter threshold, self-heal conversion. Logica pura con PGlite in-memory.
2
Integracion de processPending: Con mock ISyncHttpClient, verificar orden de prioridad, grouped operations, y reset de backoff.
3
Change-applier con datos reales: Usar PGlite in-memory para verificar SQL INSERT/UPDATE/DELETE contra schema local.

Plan de Accion

Plan por fases incremental. Cada fase es segura y no rompe funcionalidad existente.

1Fase 1: Extraer Abstracciones Testeables

Semana 1
  • Crear sync/queue.ts con PgSyncQueue
  • Crear sync/http-client.ts con SyncHttpClient
  • Unificar pull() + pullWithOptions() en un solo metodo
  • SyncService queda como facade que delega a las abstracciones

2Fase 2: Corregir Bugs Criticos

Semana 1-2
  • Agregar lifecycle guard (ready: Promise) en SyncService
  • Whitelist de columnas en change-applier (generar desde shared schema)
  • Crear sync/cleanup.ts para logout/business-switch
  • applyUpdate: convertir skip silencioso en upsert

3Fase 3: Mejorar Robustez

Semana 2-3
  • Wire SyncCoordinator a network events (online/offline)
  • Reemplazar polling con event-driven status
  • Escribir tests unitarios para SyncService via abstracciones
  • Escribir tests de integracion para change-applier con PGlite real
