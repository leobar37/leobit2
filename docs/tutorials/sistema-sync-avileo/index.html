Arquitectura del Sistema

Avileo utiliza una arquitectura híbrida que combina PostgreSQL local (PGlite), sincronización REST personalizada y manejo de conflictos server-side. Esta arquitectura permite a los vendedores trabajar 100% offline mientras mantienen la consistencia de datos.

PGlite (PostgreSQL en WASM)

Base de datos PostgreSQL completa que corre en el navegador usando WebAssembly. Persiste en IndexedDB, permite transacciones SQL completas y mantiene el esquema idéntico al servidor.

Push Sync (Client → Server)

Cola de operaciones pendientes que se sincronizan con el servidor en lotes (batches). Cada operación pasa por validación, detección de conflictos y procesamiento transaccional.

Pull Sync (Server → Client)

Sistema de cursor-based sync que trae solo los cambios desde la última sincronización. Usa paginación (100 registros por request) para manejar grandes volúmenes de datos.

Conflict Resolution

Sistema de detección de conflictos basado en versiones. Cada entidad tiene un campo version que incrementa con cada cambio. Si hay discrepancia, se detecta el conflicto y se puede aplicar estrategia "last-write-wins" o merge manual.

Estados de Sincronización

synced
Datos sincronizados con el servidor
pending
Cambios locales pendientes de subir
error
Fallo en sincronización

Flujo de Sincronización

El sistema maneja dos flujos principales: Push (subir cambios locales al servidor) y Pull (bajar cambios del servidor al cliente). Ambos funcionan de manera independiente y automática.

Flujo Push: Cliente → Servidor

Cuando un vendedor crea una venta offline, el sistema la encola y la sincroniza cuando hay conexión.

sequenceDiagram participant User participant Service participant Queue participant Server participant Engine participant DB User->>Service: Crear venta (offline) Service->>Service: Validar datos Service->>Queue: queueSync() Queue->>Queue: Generar idempotencyKey Queue->>Queue: Guardar en PGlite Note over Queue: Auto-sync cada 30s Queue->>Server: POST /sync/batch Server->>Engine: processBatch() Engine->>DB: BEGIN TRANSACTION loop Cada operacion Engine->>Engine: SAVEPOINT Engine->>Engine: Validar y Ejecutar alt Exito Engine->>DB: RELEASE SAVEPOINT else Fallo Engine->>DB: ROLLBACK TO SAVEPOINT end end Engine->>DB: COMMIT Server-->>Queue: Resultados Queue->>Queue: Actualizar sync_status

Sync Group ID: Agrupación Atómica

Operaciones relacionadas (venta + items + confirmación) se agrupan por sync_group_id para garantizar que se procesen juntas o no se procesen. 

// Ejemplo: Crear venta con items
const syncGroupId = crypto.randomUUID();

// 1. Insertar venta (parent)
await saleService.createDraft({ syncGroupId });

// 2. Agregar items (children)
await saleService.addItem({ saleId, syncGroupId });

// 3. Confirmar venta (parent update)
await saleService.confirm({ saleId, syncGroupId });

// Las 3 operaciones viajan juntas en un batch

Flujo Pull: Servidor → Cliente

El cliente consulta periódicamente el servidor por cambios usando un cursor (timestamp) para solo recibir datos nuevos.

sequenceDiagram participant Timer participant Pull participant Server participant PG participant PGlite Timer->>Pull: Trigger pull() Pull->>Pull: Cargar cursor de localStorage Pull->>Server: GET /sync/changes?since=cursor Server->>PG: Query cambios desde cursor PG->>Server: Operaciones nuevas Server-->>Pull: Cambios + nuevo cursor loop Por cada cambio Pull->>Pull: Validar tabla whitelist alt Insert o Update Pull->>PGlite: UPSERT else Delete Pull->>PGlite: DELETE end end Pull->>Pull: Guardar nuevo cursor Pull->>Pull: Invalidar queries de TanStack

Cursor-Based Sync

El cursor es un timestamp (processedAt) que indica hasta dónde el cliente ha sincronizado. Solo se traen registros con processedAt >= cursor.

UPSERT Pattern

Usamos INSERT ON CONFLICT DO UPDATE para manejar tanto inserciones como actualizaciones en una sola operación SQL.

Problema de Rendimiento

Cuando el sistema sincroniza 500-600 registros, el proceso se vuelve extremadamente lento (9-20 segundos). Este análisis identifica las causas raíz del problema.

Síntoma Principal

500-600 registros tardan 9-20 segundos en sincronizar, lo que genera una mala experiencia de usuario, especialmente en dispositivos móviles con conexión lenta.

Tiempo objetivo: < 3 segundos
1

Batch Size Muy Pequeño

Con BATCH_SIZE = 50, 500 registros requieren 10 requests HTTP separados. Cada roundtrip añade 50-200ms de latencia de red.

Cálculo:
500 registros ÷ 50 = 10 HTTP requests
10 × 150ms (promedio) = 1,500ms solo en red
2

Procesamiento Secuencial

Los cambios se aplican uno por uno en un loop. Cada cambio = 1 query SQL. 500 cambios = 500 queries secuenciales. 

// Código actual (lento)
for (const change of changes) {
  await applyChange(change); // 1 query
}
// 500 iteraciones = 500 queries
3

N+1 Query Pattern

Cada handler hace 2 queries: primero verifica si existe (findById), luego ejecuta (update/delete). 

// En cada handler
const existing = await saleRepo.findById(id); // Query 1
if (!existing) return;
await saleRepo.update(id, data);               // Query 2

// 500 ops × 2 = 1,000 queries
4

Overhead de Savepoints

Cada operación en una transacción crea un SAVEPOINT (2-5ms). Con 500 operaciones, esto suma 2,500ms adicionales. 

// Por cada operación:
await tx.execute(sql`SAVEPOINT sp_1`);      // ~2ms
// ... procesar ...
await tx.execute(sql`RELEASE SAVEPOINT`);  // ~2ms

Desglose de Tiempo (500 registros)

HTTP Roundtrips (10 requests) 1.5 - 2.0s
Savepoint Overhead (500 ops) 1.0 - 2.5s
N+1 Queries (1,000 queries) 5.0 - 10.0s
Procesamiento Secuencial 2.5 - 5.0s
Total Estimado 9 - 20 segundos

Buena Noticia

El sistema ya tiene sincronización incremental - NO está bajando toda la data cada vez. El cursor basado en processedAt asegura que solo traemos cambios nuevos. El problema es arquitectural (overhead por operación), no de diseño general.

Solución por Etapas

Para resolver el problema de rendimiento con 500-600 registros sin sacrificar la experiencia offline, implementamos una estrategia de carga priorizada: datos críticos primero, histórico en background.

Estrategia de Carga Priorizada

1
Crítica

Datos de Referencia

  • • customers
  • • products
  • • product_variants
Lookback: últimos 30 días
2
Esencial

Ventas Recientes

  • • sales
  • • sale_items
Lookback: últimos 7 días
3
Background

Histórico Completo

  • • abonos (todas las deudas)
  • • purchases
  • • distribuciones
  • • visitas, tags
Lookback: todo el histórico

¿Por Qué Funciona?

Tiempo al Primer Uso

Los vendedores pueden empezar a trabajar en < 2 segundos con los datos esenciales cargados. Las ventas de hace 7 días son suficientes para operar normalmente.

Deudas Históricas

Los abonos (pagos de deudas) se cargan en background porque un cliente puede tener deudas de hace 6 meses. Cuando el vendedor busca un cliente, el background ya cargó todo su histórico de deudas.

Carga Progresiva

En lugar de bloquear 20 segundos al inicio, la app se carga en 3-5 segundos y el resto llega silenciosamente mientras el usuario trabaja.

Flujo de Carga por Etapas

sequenceDiagram participant A as App participant C as Critical participant E as Essential participant B as Background participant U as User Note over A: Inicio de App A->>C: 1. Cargar customers, products (30 dias) C-->>A: Datos criticos listos (~1s) A->>E: 2. Cargar ventas recientes (7 dias) E-->>A: Ventas recientes listas (~1s) A->>U: App usable ahora A->>B: 3. Cargar abonos historicos B-->>A: Abonos completos A->>B: 4. Cargar purchases, distribuciones B-->>A: Datos completos Note over U: Usuario trabaja mientras el resto carga en background

Implementación

Código de referencia para implementar el sistema de sincronización por etapas. Estos ejemplos muestran los componentes clave del sistema.

StagedPullCoordinator

Coordinador que gestiona la carga por etapas, permitiendo que la app sea usable rápidamente mientras carga el histórico en background. 

// packages/app/app/lib/sync/staged-pull-coordinator.ts

import type { PullService, PullResult } from "./pull-service";
import { SYNC_STAGES } from "@avileo/shared";

interface StagedPullState {
  stage: string;
  status: "loading" | "complete" | "error";
  recordsLoaded: number;
  error?: string;
}

export class StagedPullCoordinator {
  private pullService: PullService;
  private state: Map<string, StagedPullState> = new Map();
  
  constructor(pullService: PullService) {
    this.pullService = pullService;
  }

  /**
   * Carga los datos esenciales (bloqueante)
   * La app espera a que esto complete antes de ser usable
   */
  async loadCriticalData(): Promise<PullResult> {
    this.updateState("CRITICAL", { status: "loading", recordsLoaded: 0 });
    
    const since = this.getDateDaysAgo(SYNC_STAGES.CRITICAL.lookbackDays);
    const entities = SYNC_STAGES.CRITICAL.entities;
    
    try {
      const result = await this.pullService.pull({
        entityTypes: entities,
        since: since.toISOString(),
        limit: 100,
      });
      
      this.updateState("CRITICAL", {
        status: "complete",
        recordsLoaded: result.changesApplied,
      });
      
      return result;
    } catch (error) {
      this.updateState("CRITICAL", {
        status: "error",
        recordsLoaded: 0,
        error: error instanceof Error ? error.message : "Unknown error",
      });
      throw error;
    }
  }

  /**
   * Carga ventas recientes (bloqueante)
   * Segunda etapa antes de que la app sea usable
   */
  async loadRecentSales(): Promise<PullResult> {
    this.updateState("RECENT_SALES", { status: "loading", recordsLoaded: 0 });
    
    const since = this.getDateDaysAgo(SYNC_STAGES.RECENT_SALES.lookbackDays);
    const entities = SYNC_STAGES.RECENT_SALES.entities;
    
    const result = await this.pullService.pull({
      entityTypes: entities,
      since: since.toISOString(),
      limit: 100,
    });
    
    this.updateState("RECENT_SALES", {
      status: "complete",
      recordsLoaded: result.changesApplied,
    });
    
    return result;
  }

  /**
   * Carga histórico completo (background)
   * No bloquea - el usuario puede usar la app mientras carga
   */
  async loadHistoricalData(): Promise<void> {
    this.updateState("HISTORICAL", { status: "loading", recordsLoaded: 0 });
    
    const entities = SYNC_STAGES.HISTORICAL.entities;
    let totalLoaded = 0;
    let hasMore = true;
    
    // Cargar en batches hasta completar
    while (hasMore) {
      const result = await this.pullService.pull({
        entityTypes: entities,
        limit: 200,  // Batch más grande para background
      });
      
      totalLoaded += result.changesApplied;
      hasMore = result.hasMore;
      
      this.updateState("HISTORICAL", {
        status: hasMore ? "loading" : "complete",
        recordsLoaded: totalLoaded,
      });
      
      // Pequeña pausa para no saturar el dispositivo
      if (hasMore) {
        await this.sleep(500);
      }
    }
  }

  /**
   * Orquesta toda la carga
   * Devuelve control después de las etapas bloqueantes
   */
  async executeStagedLoad(): Promise<{
    critical: StagedPullState;
    recent: StagedPullState;
  }> {
    // Etapa 1: Crítica (bloqueante)
    await this.loadCriticalData();
    
    // Etapa 2: Reciente (bloqueante)
    await this.loadRecentSales();
    
    // App usable ahora - iniciar background
    this.loadHistoricalData().catch(console.error);
    
    return {
      critical: this.state.get("CRITICAL")!,
      recent: this.state.get("RECENT_SALES")!,
    };
  }

  private getDateDaysAgo(days: number): Date {
    const date = new Date();
    date.setDate(date.getDate() - days);
    return date;
  }

  private updateState(stage: string, state: Partial<StagedPullState>): void {
    const current = this.state.get(stage) || { stage, status: "loading", recordsLoaded: 0 };
    this.state.set(stage, { ...current, ...state });
  }

  private sleep(ms: number): Promise<void> {
    return new Promise(resolve => setTimeout(resolve, ms));
  }
}

Backend: GET /sync/changes

Endpoint que soporta filtrado por entidad y rango de fechas para la carga por etapas. 

// packages/backend/src/api/sync.ts

.get("/changes", async ({ syncService, ctx, query }) => {
  // Parse cursor (timestamp)
  let since: Date | undefined;
  if (query.since) {
    since = new Date(query.since);
  }

  // Parse entity types filter (e.g., "sales,customers")
  const entityTypes = query.entityTypes
    ? query.entityTypes.split(",").filter(isValidEntity)
    : undefined;

  // Parse limit (capped at 500)
  const limit = Math.min(
    parseInt(query.limit || "100", 10),
    500
  );

  // Parse priority for ordering
  const priority = query.priority as "high" | "low" | undefined;

  const result = await syncService.getChanges(ctx, since, limit, {
    entityTypes,
    priority,
  });

  return {
    changes: result.changes,
    nextSince: result.nextSince,
    hasMore: result.hasMore,
  };
})

SyncService: Query con Filtros

// packages/backend/src/services/sync/sync.service.ts

async getChanges(
  ctx: RequestContext,
  since?: Date,
  limit = 100,
  options?: {
    entityTypes?: string[];
    priority?: "high" | "low";
  }
): Promise<SyncChangesResult> {
  const baseConditions = [
    eq(syncOperations.businessId, ctx.businessId),
    eq(syncOperations.status, "processed"),
  ];

  // Filter by cursor (incremental sync)
  if (since) {
    baseConditions.push(gte(syncOperations.processedAt, since));
  }

  // Filter by entity types (staged loading)
  if (options?.entityTypes?.length) {
    baseConditions.push(
      inArray(syncOperations.entity, options.entityTypes)
    );
  }

  // Priority ordering
  const orderBy = options?.priority === "high"
    ? [
        asc(syncOperations.processedAt),
        // Critical entities first
        sql`CASE entity 
          WHEN 'customers' THEN 1 
          WHEN 'products' THEN 1
          WHEN 'sales' THEN 2
          ELSE 99 END`
      ]
    : [asc(syncOperations.processedAt)];

  const operations = await db.query.syncOperations.findMany({
    where: and(...baseConditions),
    orderBy,
    limit: limit + 1, // +1 to detect hasMore
  });

  // Build changes array
  const changes = operations.slice(0, limit).map(op => ({
    entity: op.entity,
    entityId: op.entityId,
    operation: op.operation,
    payload: op.payload,
    processedAt: op.processedAt,
  }));

  return {
    changes,
    nextSince: operations[operations.length - 1]?.processedAt?.toISOString(),
    hasMore: operations.length > limit,
  };
}
