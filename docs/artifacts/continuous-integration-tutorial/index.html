Continuous Integration

Una práctica de desarrollo de software donde cada miembro del equipo integra sus cambios al menos una vez al día, verificando cada integración con un build automático.

Artículo de Martin Fowler · Enero 2024

1 ¿Qué es Continuous Integration?

Definición Core

Cada desarrollador integra su código al mainline compartido al menos diariamente. Cada integración se verifica automáticamente para detectar errores lo antes posible.

3 Las 11 Prácticas de CI

1

Version Controlled Mainline

Todo en VCS: código, tests, schema, config. Un solo branch compartido.

2

Automated Build

Build con un solo comando. Sin clicks ni procesos manuales.

3

Self-Testing Build

Tests automatizados que verifican el código. Frameworks xUnit.

4

Daily Commits

Todos hacen push al mainline al menos una vez al día.

5

CI Service on Mainline

Cada push dispara un build automático en entorno de referencia.

6

Fix Broken Builds Immediately

"Nobody has a higher priority task than fixing the build"

7

Keep the Build Fast

Guideline: menos de 10 minutos para commit build.

8

Hide Work-in-Progress

Feature flags, Keystone Interfaces para integrar código incompleto.

9

Test in Production Clone

Mismo SO, DB, librerías, hardware que producción.

10

Everyone Can See Results

Dashboards, notifications, displays físicos del estado del build.

11

Automated Deployment

Scripts para deploy a cualquier ambiente automáticamente.

5 Beneficios de CI

Reduced Delivery Risk

Integraciones pequeñas = menos incertidumbre. El peor caso es perder menos de un día de trabajo.

Less Time Wasted

Relación no lineal: 2x código = 4x tiempo de integración. CI evita esta trampa.

Less Bugs

Self-testing + detección rápida. DORA research: elite teams tienen menos fallos.

Enables Refactoring

Sin CI, refactors grandes causan integraciones doloras. CI permite refactors pequeños y frecuentes.

Release is a Business Decision

Release-Ready Mainline = deploy en minutos. Stakeholders deciden cuándo, no el código.

Team Visibility

Todos ven el estado del sistema. CI es comunicación, no solo tecnología.

Key Takeaways

CI ≠ CI Service

Jenkins/GitHub Actions son herramientas, no CI en sí. Correr CI en feature branches es semi-integración.

Self-Testing es prerrequisito

Sin tests automatizados, CI no funciona. TDD es la mejor forma de lograrlos.

Integrar antes de "completar"

Feature flags permiten integrar código incompleto sin exponerlo a users.

10 minutos o menos

Si el build tarda más, implementar deployment pipeline con stages.
