Diferencias Clave: Frontend vs Backend

Aspecto Frontend (PGlite) Backend (PostgreSQL)
Propósito Cola de operaciones pendientes (push) Operaciones procesadas exitosamente
Estados pending → processing → syncing → completed/failed/conflict/deadLetter pending → processed/failed
Dead Letter Sí (sync_dead_letter) No (solo sync_conflicts)
Coalescing Sí (create+delete=cancel) No
Columnas entity_type, operation, entity_id entity, action, entityId

Esquema Frontend: sync_operations (PGlite)

CREATE TABLE sync_operations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  business_id UUID NOT NULL,
  entity_type TEXT NOT NULL,          -- 'customers', 'sales', 'abonos', etc.
  entity_id TEXT NOT NULL,            -- ID de la entidad afectada
  sync_group_id TEXT,               -- Agrupación atómica de operaciones
  operation TEXT NOT NULL,            -- 'create' | 'update' | 'delete'
  payload JSONB,                      -- Datos de la operación
  status TEXT NOT NULL DEFAULT 'pending',
  version INTEGER NOT NULL DEFAULT 1, -- Control de concurrencia optimista
  sync_attempts INTEGER NOT NULL DEFAULT 0,
  last_error TEXT,                    -- Último error de sincronización
  last_attempt_at TIMESTAMP,        -- Último intento
  idempotency_key TEXT UNIQUE,      -- Clave de idempotencia
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Índices para performance
CREATE INDEX idx_sync_ops_entity ON sync_operations(business_id, entity_type, entity_id);
CREATE INDEX idx_sync_ops_status ON sync_operations(business_id, status);
CREATE INDEX idx_sync_ops_group ON sync_operations(business_id, sync_group_id);

Flujo Frontend: Desde la UI hasta el Backend

1

Usuario realiza acción (crear/editar/eliminar)

// Ejemplo: Crear cliente
await customerService.create({
  name: "Juan Pérez",
  phone: "999888777"
});
2

BaseService inserta en tabla local con sync_status='pending'

// 1. Inserta en tabla local (ej. customers)
await pg.query(
  `INSERT INTO customers (id, name, sync_status) VALUES ($1, $2, 'pending')`,
  [customerId, data.name]
);

// 2. Encola operación de sync
await syncService.enqueue({
  entity_type: 'customers',
  operation: 'create',
  entityId: customerId,
  data: { name: data.name, ... }
});
3

PgSyncQueue: Coalescing y Encolamiento

Lógica de coalescing (PgSyncQueue.enqueue):

  • • Si existe operación para misma entidad → aplica coalescing
  • • create + delete = cancela ambas (la entidad nunca llegó al servidor)
  • • update + update = merge (combina cambios)
  • • create + update = replace (solo el create con datos actualizados)
4

SyncAutoRunner: Envío automático periódico

// Corre cada SYNC_INTERVAL_MS (5 segundos)
SyncAutoRunner.start(() => {
  return syncService.processPending();
}, SYNC_INTERVAL_MS);

// Usa backoff exponencial si hay errores:
// 1s → 2s → 4s → 8s → 16s → 30s (max)
5

SyncBatchProcessor: Envío al Backend

// 1. Obtiene operaciones pendientes (ordenadas por prioridad)
const pending = await queue.getPending(BATCH_SIZE, { includePriority: true });
// Prioridad: customers/products (1) → variants (2) → sales/abonos (3)

// 2. Envía al backend
const response = await httpClient.postBatch(operations);

// 3. Procesa resultados
for (const result of response.results) {
  if (result.success) await lifecycle.markCompleted(id);
  else if (result.conflict) await lifecycle.markConflict(id, result.conflict);
  else await lifecycle.markFailed(id, result.error);
}

Dead Letter Queue (Frontend)

CREATE TABLE sync_dead_letter (
  id UUID PRIMARY KEY,
  business_id UUID NOT NULL,
  operation_id UUID NOT NULL,       -- Referencia a sync_operations.id
  entity_type TEXT NOT NULL,
  operation TEXT NOT NULL,
  entity_id TEXT NOT NULL,
  data JSONB,                       -- Datos originales
  error TEXT,                       -- "Max retries exceeded"
  sync_attempts INTEGER,            -- Número de intentos
  original_error TEXT,              -- Error original
  created_at TIMESTAMP
);

Cuando una operación falla más de MAX_RETRIES (5) veces, se mueve a sync_dead_letter. El usuario puede:

  • • Reintentar manualmente (retryDeadLetterOperation)
  • • Eliminar permanentemente
  • • Resolver conflictos si aplica

Esquema Backend: sync_operations (PostgreSQL)

// Drizzle ORM Schema
export const syncOperations = pgTable("sync_operations", {
  id: uuid("id").primaryKey().defaultRandom(),
  businessId: uuid("business_id").notNull().references(() => businesses.id),
  operationId: varchar("operation_id", { length: 128 }).notNull(),  // Idempotencia
  entity: varchar("entity", { length: 64 }).notNull(),              // Tipo entidad
  action: varchar("action", { length: 32 }).notNull(),               // create/update/delete
  entityId: varchar("entity_id", { length: 128 }).notNull(),
  syncGroupId: varchar("sync_group_id", { length: 128 }),          // Agrupación atómica
  payload: jsonb("payload").$type<Record<string, unknown>>().notNull(),
  status: varchar("status", { length: 32 }).notNull().default("pending"),
  error: text("error"),
  clientTimestamp: timestamp("client_timestamp").notNull(),
  processedAt: timestamp("processed_at"),                          // Cuando se procesó
  
  // Tracking multi-dispositivo
  deviceId: varchar("device_id", { length: 128 }),
  sourceFingerprint: varchar("source_fingerprint", { length: 256 }),
  
  createdAt: timestamp("created_at").notNull().defaultNow(),
}, (table) => [
  index("idx_sync_operations_business_id").on(table.businessId),
  index("idx_sync_operations_status").on(table.status),
  uniqueIndex("uq_sync_operations_business_operation")
    .on(table.businessId, table.operationId),  // Idempotencia
]);

Nota: A diferencia del frontend, el backend usa nombres diferentes: entity (no entity_type), action (no operation), entityId (no entity_id). Solo tiene 3 estados: pending, processed, failed.

Flujo Backend: SyncEngine.processBatch()

1. Recepción y Ordenamiento

// Ordena por dependencias (padres antes que hijos)
const sorted = OperationSorter.sort(operations);
// customers, products (1) → variants, groups (2) → sales, abonos (3)

2. Transaction + Savepoints

await db.transaction(async (tx) => {
  for (let i = 0; i < operations.length; i++) {
    const savepointName = `sp_op_${i}`;
    await tx.execute(sql.raw(`SAVEPOINT ${savepointName}`));
    
    try {
      const result = await processOperation(...);
      await tx.execute(sql.raw(`RELEASE SAVEPOINT ${savepointName}`));
    } catch (error) {
      await tx.execute(sql.raw(`ROLLBACK TO SAVEPOINT ${savepointName}`));
      // Continúa con la siguiente operación
    }
  }
});

Cada operación tiene su savepoint: si falla, solo se revierte esa operación, no toda la transacción.

3. Idempotencia Check

const existing = await syncOpRepo.findByIdempotencyKey(
  ctx, 
  operation.idempotencyKey
);

if (existing?.status === "processed") {
  return { success: true };  // Ya procesado, no repetir
}

4. Conflict Detection

const conflict = await ConflictResolverRegistry
  .getResolver(entityType)
  .checkConflict(ctx, operation, tx);

if (conflict.hasConflict) {
  // Persiste en sync_conflicts para resolución admin
  await syncConflictRepo.create(ctx, {
    operationId: operation.idempotencyKey,
    entityType, entityId,
    localData: operation.payload,
    serverData: conflict.serverData,
    localVersion: operation.localVersion,
    serverVersion: conflict.serverVersion,
  });
  return { success: false, conflict };
}

5. Entity Handler Execution

const handler = HandlerRegistry.getHandler(entityType, deps);

// Pipeline: validateBusinessRules → execute
const result = await syncPipeline.execute(
  context,      // ctx, correlationId
  operation,    // datos de la operación
  handler,      // handler específico de entidad
  tx            // transacción
);

// Handler examples:
// - CustomerSyncHandler.create() → customerRepo.create()
// - SaleSyncHandler.update() → saleRepo.update()
// - AbonoSyncHandler.delete() → paymentRepo.delete()

6. Persistir Resultado

// Enriquece payload con syncStatus: 'synced'
const enrichedPayload = {
  ...operation.payload,
  syncStatus: "synced",
  syncAttempts: 0,
};

await syncOpRepo.updateStatus(
  ctx,
  operation.idempotencyKey,
  result.success ? "processed" : "failed",
  result.error ?? null,
  tx,
  enrichedPayload
);

Tabla: sync_conflicts

Cuando hay conflictos de versión (optimistic concurrency), se guardan en esta tabla para resolución manual por administrador:

CREATE TABLE sync_conflicts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  business_id UUID NOT NULL,
  operation_id TEXT NOT NULL,         -- idempotencyKey
  entity_type TEXT NOT NULL,
  entity_id TEXT NOT NULL,
  local_data JSONB NOT NULL,          -- Datos del cliente
  server_data JSONB NOT NULL,           -- Datos actuales en servidor
  local_version INTEGER NOT NULL,
  server_version INTEGER NOT NULL,
  status TEXT DEFAULT 'pending',      -- pending/resolved/rejected
  resolution_type TEXT,               -- server/local/merge
  resolved_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT now()
);

1. GET /sync/changes

El frontend pide cambios desde su último cursor:

GET /sync/changes?cursor={timestamp_opId}&entityTypes=customers,sales

2. Backend Query

Busca operaciones procesadas después del cursor:

SELECT * FROM sync_operations 
WHERE business_id = ? 
  AND status = 'processed'
  AND (processed_at, operation_id) > (?, ?)
ORDER BY processed_at, operation_id
LIMIT 500

3. Frontend Apply

ChangeApplier aplica cada cambio:

for (const change of changes) {
  await applier.applyChange({
    entityType: change.entity,
    entityId: change.entityId,
    operation: change.action, // create/update/delete
    data: change.payload,
  });
}

4. Staged Sync

Estrategia de 3 etapas:

  • • CRITICAL: customers, products (inmediato)
  • • RECENT_SALES: ventas últimas 24h
  • • HISTORICAL: datos antiguos (lazy)

Estados Frontend (sync_operations)

pending

Operación encolada, esperando ser sincronizada. Estado inicial después de enqueue().

processing

Operación está siendo preparada para envío (marcada antes de HTTP request).

syncing

Operación está siendo enviada al backend (durante HTTP request).

completed

Operación sincronizada exitosamente. El servidor confirmó el procesamiento.

failed

Error en sincronización. Se reintentará con backoff exponencial (hasta MAX_RETRIES).

conflict

Conflicto de versión detectado. Requiere resolución manual (server/local/merge).

deadLetter

Máximo de reintentos excedido. Movida a sync_dead_letter. Requiere intervención manual.

Estados Backend (sync_operations)

El backend tiene un modelo más simple (solo registra operaciones procesadas):

pending

Operación recibida, en proceso de validación y ejecución.

processed

Operación ejecutada exitosamente en la base de datos.

failed

Error al ejecutar la operación (validación, DB error, etc.). Se guarda el error.
