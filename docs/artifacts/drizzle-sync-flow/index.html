Biblioteca de sincronización offline-first para PostgreSQL y PGlite

Flujo General de Sincronización

📤

Push (Envío)

El frontend encola operaciones locally en PGlite y las envía en batch al backend via POST /sync/batch

🔄

Pull (Recepción)

El frontend polléa cambios del servidor via GET /sync/changes con cursor-based pagination

⚠️

Conflictos

El ConflictResolver detecta versiones desfasadas y los persiste para resolución admin

Flujo de Push — De Frontend a Backend

Cómo las operaciones locales llegan a la base de datos y se distribuyen

Idempotencia

Cada operación tiene un idempotencyKey único (cliente genera). Si el servidor ya la procesó, retorna el resultado anterior sin re-ejecutar.

// Cliente genera la key
const key = `${deviceId}:${entityId}:${operation}:${localTimestamp}`;
// Si el server ya la procesó → returns { success: true } sin ejecutar de nuevo

Savepoints (Rollback Parcial)

El SyncEngine usa PostgreSQL savepoints. Si una operación falla, solo esa operación hace rollback — las demás del batch siguen.

// Por cada operación:
SAVEPOINT sp_op_0;
// ... execute handler ...
RELEASE SAVEPOINT sp_op_0;
// Si falla → ROLLBACK TO sp_op_0

Ordenamiento Topológico — OperationSorter

Garantiza que los padres se procesen antes que los hijos usando un sort topológico basado en FK

EntityRegistry — Optimización en Batch

Dentro de un mismo batch, si un handler necesita verificar que un padre existe, el EntityRegistry evita queries redundantes a la DB.

// En BaseSyncHandler.ensureParentExists():
if (this.registry?.wasCreated(parentId)) {
  return; // Skip DB query — el padre se creó en este batch
}
const parent = await findInDb(); // Solo si no está en registry

Eventos Compuestos — Ventas con Múltiples Líneas

Cómo la librería resuelve escenarios donde una venta tiene múltiples eventos asociados

ConflictResolver — Detección de Versiones

Cada entidad tiene un version campo. Si la versión del cliente es menor que la del servidor, hay conflicto.

last-write-wins

tags, products, abonos — no hay versión, gana el último write

version-based

sales — usa columna version para detectar conflictos

conflict persisted

Si hay conflicto → se guarda en sync_conflicts para resolución admin

Flujo de Pull — Del Backend a los Clientes

Estrategia de 3 etapas para distribuir cambios: CRITICAL → RECENT_SALES → HISTORICAL

Cursor-based Pagination

El cursor es un timestamp (updated_at). Se persiste en local storage para sobrevivir recargas.

GET /sync/changes?since=2024-01-15T10:30:00Z&limit=100
// Response:
{ data: { changes: [...], nextSince: "...", hasMore: true } }

Auto-pull

PullService hace polling automático cada PULL_INTERVAL_MS (default 5s) cuando está online.

// Stops when offline, resumes when back
if (isOnlineFn() && !isPullingFlag) {
  await pull();
}

Sistema de Eventos

Eventos tipados para observabilidad de sync (push:complete, pull:stale, conflict:detected, etc.)
