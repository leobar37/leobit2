Arquitectura de Sincronización

Biblioteca extraída para sincronización bidireccional entre PGlite (PostgreSQL WASM) y PostgreSQL server. Offline-first con resolution de conflictos y coalescing de operaciones.

Visión General de la Arquitectura

PgSyncQueue — Cola Local

Implementa ISyncQueue usando PGlite para almacenamiento local. Gestiona operaciones pending, failed y dead letter.

// Enqueue con coalescing
await queue.enqueue({
entity_type: 'sales',
entityId: 'sale_123',
operation: 'create',
data: { amount: 150 }
});
Idempotency key para evitar duplicados
Coalescing: create+delete=cancel, update+update=merge
Dead letter queue para operaciones fallidas

PullService — Fetch Cambios

Cursor-based pagination para obtener cambios del servidor. Detecta condiciones de stuck (cursor sin avanzar).

// Fetch cambios desde servidor
const result = await pullService.pull();
// Cursor-based, auto-retry
// Stale detection: MAX_STALE_PULLS=5
Exponential backoff en errores
Staged pull: CRITICAL → RECENT_SALES → HISTORICAL
forceReset() para recovery

SyncEngine — Motor de Procesamiento

Procesa batches de operaciones sync con savepoints PostgreSQL. Cada operación tiene su propio savepoint para rollback parcial.

// Procesar batch de operaciones
const result = await engine.processBatch(ctx, ops);
// Result:
{ succeeded: 5, failed: 1, conflicts: 0 }
Per-operation savepoints (atomic batch)
Idempotency via idempotency_key
Event emission (push:complete, conflict:detected...)

EntityRegistry — Batch Tracking

Tracking in-memory de entidades creadas/modificadas dentro del batch. Evita queries redundantes a la DB cuando el padre ya fue creado en el mismo batch.

// Registry tracking during batch
registry.register('create', 'sale_123');
// Handler checks registry before DB query
if (registry.wasCreated(parentId)) return;

ConflictResolver — Detección de Conflictos

Version-based conflict detection comparando client version vs server version. Conflictos persistidos para resolución manual por admins.

// Conflict detected
{
clientVersion: 3,
serverVersion: 5,
serverData: {'{...}'}
}

PUSH — Cliente → Servidor

1
App write operation

App writes to PGlite locally, operation enqueued to sync queue.

syncService.enqueue({ entity_type: 'sales', operation: 'create', data: {...} })
2
Coalescing

Multiple operations on same entity merged/cancelled. E.g., create+update → single create with merged payload.

3
Batch push

Auto-runner batches pending operations and POSTs to /sync/batch.

POST /sync/batch → [{ idempotencyKey, entityType, operation, payload, localVersion }]
4
Server processing

SyncEngine sorts by priority, uses savepoints for per-op rollback, detects conflicts.

5
Response

Array of results: [{ success: true, idempotencyKey: '...' }, { success: false, conflict: {...} }]

PULL — Servidor → Cliente

1
Fetch changes

PullService GET /sync/changes?since={cursor}&limit=100

GET /sync/changes?since=cursor_abc123&limit=100
2
Cursor-based pagination

Server returns changes with next cursor. Client persists cursor before applying changes (crash safety).

3
Apply changes

Changes applied to PGlite via UPSERT operations. Conflicts detected against local pending ops.

4
Query invalidation

TanStack Query caches invalidated for affected entity types.

Conflict Resolution Flow

1. Detect

Server compares clientVersion vs serverVersion

2. Persist

Conflict stored in sync_conflicts table for admin resolution

3. UI Resolution

Admin picks: server wins / local wins / manual merge

2. Setup Frontend — React Provider

app/root.tsx — Wrap app with SyncProvider
import { SyncProvider } from "@avileo/drizzle-sync/react";
import { createSyncRuntime } from "@avileo/drizzle-sync/pglite";
import { pg } from "./lib/db";
import { apiClient } from "./lib/api-client";
// Create runtime singleton
const runtime = createSyncRuntime({
db: pg,
apiClient: {
pushBatch: async (ops) => await apiClient.post("/sync/batch", ops),
fetchChanges: async (cursor) => await apiClient.get("/sync/changes", { since: cursor }),
},
});
export default function App() {
return (
<SyncProvider runtime={runtime}>
<Outlet />
</SyncProvider>
);
}

3. Setup Backend — ElysiaJS Route

backend/src/api/sync.ts — Sync endpoint
import { SyncEngine } from "@avileo/drizzle-sync/server";
import { db } from "../lib/db";
import * as schema from "../db/schema";
// Create engine with handlers
const engine = new SyncEngine(db, {
handlers: [
new SalesHandler(),
new CustomerHandler(),
// ... more handlers
],
});
// Elysia route
const syncRouter = new Elysia()
.post("/sync/batch", async ({ body, user }) => {
const ctx = { businessId: user.businessId, userId: user.id };
return await engine.processBatch(ctx, body);
})
.get("/sync/changes", async ({ query, user }) => {
// Fetch changes since cursor
return await fetchChanges(db, user.businessId, query.since);
});

Display sync status
import { useSyncState } from "@avileo/drizzle-sync/react";
function SyncIndicator() {
const { pendingCount, isSyncing } = useSyncState();
return (
<div>
{isSyncing ? "Syncing..." : `Pending: ${pendingCount}`}
</div>
);
}
Manual sync trigger
import { runtime } from "~/lib/sync";
// Force immediate sync
await runtime.push();
await runtime.pull();
Handle failed operations
import { useSyncStatus } from "@avileo/drizzle-sync/react";
function SyncErrors() {
const { hasFailed, failedCount } = useSyncStatus();
if (hasFailed) {
return <Alert variant="destructive">
{failedCount} operations failed
</Alert>;
}
return null;
}

5. Custom Entity Handler (Backend)

import { BaseSyncHandler } from "@avileo/drizzle-sync/server";
class ProductHandler extends BaseSyncHandler {
entityType = "products";
async execute(ctx, op) {
switch (op.operation) {
case "create":
return this.create(ctx, op);
case "update":
return this.update(ctx, op);
case "delete":
return this.delete(ctx, op);
}
}
}
