Flujo de Ventas

Arquitectura offline-first con sincronización REST

Entidades Principales

Sale

Transacción principal. Contiene totales, tipo de pago, fecha y estado.

SaleItem

Líneas de producto. Cantidad, precio unitario, subtotal.

Customer

Cliente asociado. Opcional en ventas de contado.

Abono

Pagos o abonos del cliente sobre una venta a crédito.

Tipos de Venta

Transacción

Venta Instantánea

  • Venta realizada y cerrada en el momento
  • Flujo: draft → active → delivered/cancelled
  • Puede ser contado o crédito
Transacción

Pre-orden

  • Pedido para entrega futura
  • Flujo: draft → confirmed → delivered → cancelled
  • Permite ajustes en precio y cantidad al entregar

Máquina de Estados

Flujo Completo de Creación

1 FRONTEND - App Móvil (PGlite Local)

1. Crear Borrador
createDraft(saleInput)
  • • Genera syncGroupId
  • • Inserta en PGlite
  • • status: "draft"
  • • syncStatus: "pending"
2. Agregar Items
addItem(saleId, item)
  • • Inserta sale_items
  • • Actualiza totales
  • • Mismo syncGroupId
3. Confirmar
confirm() / confirmPreOrder()
  • • Actualiza status
  • • Incrementa version
  • • Activa sync

2 SINCRONIZACIÓN - Cola Offline

SyncService.processPending()
Agrupa por syncGroupId → POST /api/sync
sync_operations idempotencyKey savepoints

3 BACKEND - Servidor (PostgreSQL Neon)

4. SyncEngine.processBatch()
  • • Recibe operaciones en batch
  • • Ordena por dependencia (creations primero)
  • • Procesa en savepoints
  • • Dispatch a SaleSyncHandler
5. SaleRepository.update()
  • • Valida con Zod schemas
  • • Verifica version (optimistic locking)
  • • Transacción atómica
  • • Respuesta: { success, serverTimestamp }

Tipos de Pago

Pago Total

paymentMode: "pago_total"

Cliente paga el monto completo al momento.

A Cuenta

paymentMode: "a_cuenta"

Cliente paga una parte. Genera abonos pendientes.

Debe Todo

paymentMode: "debe_todo"

Venta a crédito sin pago inicial.

Patrones de Diseño Clave

Local-First

Todas las operaciones funcionan offline contra PGlite local. La sincronización ocurre en segundo plano automáticamente.

Optimistic Locking

El campo version previene conflictos de modificación concurrente entre dispositivos.

Grupos Atómicos

syncGroupId agrupa operaciones relacionadas (venta + items) para procesamiento atómico.

Idempotencia

Las operaciones pueden reintentarse de forma segura mediante idempotencyKey.
