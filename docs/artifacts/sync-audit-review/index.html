Revisión profunda del sistema sync: cómo funciona, qué está roto, y qué falta testear.

1 Cómo funciona el sistema de sync

El sistema es bidireccional y offline-first. Los datos se escriben primero en la base local (PGlite/IndexedDB) y luego se sincronizan con el servidor.

Flujo de datos bidireccional

PUSH (Cliente → Servidor)
  • • Cada 5 segundos si hay conexión
  • • Agrupa hasta 100 operaciones
  • • POST /sync/batch
  • • Retry con exponential backoff
  • • Cola muerta después de 5 intentos
PULL (Servidor → Cliente)
  • • Cada 10 segundos si hay conexión
  • • Cursor-based pagination
  • • GET /sync/changes
  • • 3 etapas: CRITICAL → RECENT → HIST
  • • Aplica cambios a PGlite local
CONFlictos
  • • Por versión (sales) o timestamp
  • • Se almacenan para resolución manual
  • • 3 estrategias: server/local/merge
  • • Self-healing: update → create

2 Los 6 hallazgos del аудит

CRÍTICO

DELETE sin businessId — riesgo de multi-tenancy

En change-applier.ts, la función applyDelete ejecuta:

DELETE FROM "sales" WHERE id = $1

Debería incluir AND business_id = $2 para asegurar que el delete es solo para el negocio correcto. Sin esto, si hay un bug de IDs, un negocio podría borrar datos de otro.

CRÍTICO

Dos PullService corriendo en paralelo

El PullSyncWrapper (usado en _protected.tsx) crea su propio PullService, independiente del que crea ServicesProvider. Ambos:

  • Tienen su propio interval (cada 10s)
  • Tienen su propio cursor en localStorage
  • LLaman a GET /sync/changes simultáneamente

Resultado: duplicación de requests, posible desincronización de cursores, y trabajo redundante.

MODERADO

Sin AbortController en requests de red

Ni sendBatch() (push) ni executePull() (pull) aceptan AbortSignal. Si el usuario navega away o el componente se desmonta, el request continúa.

Puede causar: wasted bandwidth, state updates en componentes desmontados, y memory leaks en móvil.

MODERADO

Backoff no es cancellable

El setTimeout del backoff exponencial no puede cancelarse. Si el servicio se detiene durante el wait, el timer sigue corriendo y puede causar comportamiento inesperado al reiniciar.

MODERADO

Staged pull sin mecanismo de abort

El StagedPullCoordinator hace loop while(hasMore) cargando 3 etapas de datos. Si el usuario navega o pierde conexión, no hay forma de abortar.

Además, no verifica navigator.onLine dentro del loop.

! El Bug Crítico Explicado — Doble PullService

⚠️ Este es el hallazgo más importante. No es código legacy muerto — está activo en producción.

Dos componentes crean PullServices independientes. Ambos hacen pull cada 10 segundos.

Arquitectura actual (con bug)

Qué debería pasar

Un solo PullService en el SyncCoordinator. Un solo interval. Un solo cursor en localStorage.

Qué pasa ahora

Dos PullServices con cursores separados. Ambas llaman al servidor cada 10s. El cursor de una puede sobreescribir al de la otra.

! Bug del Cursor — Infinite Retry Loop

Este bug no fue mencionado en el plan original pero lo encontré validándolo. Ocurre cuando el servidor devuelve cambios pero todos fallan al aplicarse localmente.

// pull-service.ts línea 350
if (nextSince && appliedCount > 0) {
// Solo guarda cursor si SE APLICARON cambios
this.saveCursor(nextSince);
}
1

El servidor devuelve 5 cambios y hasMore: true

2

Los 5 cambios fallan al aplicarse (ej: mismatch de schema entre server y local)

3

appliedCount === 0 → el cursor NO avanza

4

hasMore: true → el loop continúa

5

Vuelve al paso 1 — loop infinito

Fix: guardar siempre el cursor cuando nextSince existe, sin importar appliedCount.
