¿Por qué es lenta la venta directa con 100+ ventas?

El usuario reporta que al abrir Crear Venta → Asignar Cliente, todo se vuelve lento o super lento. El problema está en cómo se cargan los clientes cuando no hay búsqueda activa.

❌
findByBusiness() SIN límite
100%
clientes renderizados sin paginación
3x
queries en findById() por cada venta

Root Cause 2: findById() triplica queries en cada mutation

SaleService.findById() — 3 queries cada vez
pg.query("SELECT * FROM sales WHERE id = $1")
pg.query("SELECT id, name, dni, phone FROM customers WHERE id = $1")
pg.query("SELECT * FROM sale_items WHERE sale_id = $1")
confirm() → llama findById() antes de UPDATE
addItem() → llama findById() para buscar duplicados

sync_operations — Missing Index

Every enqueue, processBatch, and getStatus hits an unindexed table. As queue grows (every sale create/update = 1+ ops), queries degrade linearly.

❌ No index: sync_operations(business_id, status)

COUNT(*) on every filter change

Changing tabs or search fires a full table COUNT(*) scan every time, even before the user finishes typing. Blocks the UI.

Debounce helps search, but tab changes are instant and fire a new count.

No list virtualization

100 SaleCard components mount simultaneously. Each has useDeleteSale + useConfirmDialog hooks with their own contexts. Low-end mobile devices will jank during scroll.

SaleCard also calls useSale/useSaleItems indirectly — 4+ hooks per visible card.

Cascade query invalidation

useFinalizeSale invalidates 4 query families after every mutation. This triggers 4 background refetches. With many pending syncs, this creates a thundering herd on the next sync cycle.

["sales-new", id] + ["sales-new"] + ["accounts-receivable"] + ["customers-new"]

LIKE with leading wildcard

Search uses LIKE '%pattern%' which cannot use B-tree indexes. Every keystroke (after 300ms debounce) triggers a full table scan filtered by business_id.

Extra query per item operation

addItem, updateItem, removeItem all call getSaleSyncGroupId() (extra SELECT) before queueing. Each item change = 1 extra round-trip to PGlite.

findById called on every mutation

confirm, cancel, addItem, updateItem all call findById() which runs 3 separate queries (sale + customer + items) before modifying anything. Acceptable for single ops, but compounds with bulk actions.

1. Add sync_operations index

High impact, low effort. One migration:

CREATE INDEX idx_sync_operations_business_status
ON sync_operations(business_id, status);

2. Cache COUNT query

Add 5-10s cache TTL to the total count, or debounce count to fire 500ms after filter stability. Remove from initial render.

3. Confirm sales compound index

Verify idx_sales_business_saledate exists in PGlite schema for ORDER BY + filter performance.

4. Virtualize the list

Implement @tanstack/react-virtual — only render visible cards + small overscan. Major improvement on low-end mobile.

5. Reduce cascade invalidation

Use queryClient.setQueryData for targeted updates instead of invalidating 4 query families on every finalize.

6. Fold getSaleSyncGroupId into existing query

addItem already fetches items — return sync_group_id from that same query instead of making a separate call.
