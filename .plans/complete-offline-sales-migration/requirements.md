# Complete Offline Sales Migration Requirements

## Objective

Complete the offline-first migration for the vendor flow covering customers, sales, sale items, and cobros/abonos so the local app, backend sync API, sync handlers, schema definitions, conflict handling, and tests all use the same contracts and can prove a real offline-to-online round trip.

## Scope

- In scope: customer CRUD sync, sale header sync, sale item sync, abono sync, local service hooks, sync operation metadata, conflict/versioning behavior, schema parity, generated artifacts, and test validation.
- In scope: minimal UI and hook changes needed to exercise create/update/delete lifecycle for abonos and core sale payment actions.
- Out of scope: non-core modules such as purchases, distribuciones, inventory, WhatsApp, public sharing, and broad redesign.
- Out of scope: new sync framework design beyond fields and behavior needed by the current drizzle-sync engine.

## Functional Requirements

- `FR-001` - The system must use one canonical sync entity name for payments/cobros across frontend service lookup, local queue, backend API, backend handlers, and tests.
- `FR-002` - Shared schema, backend schema, generated frontend schema, and sync payload schemas must agree for `customers`, `sales`, `sale_items`, and `abonos` on columns, required fields, nullability, version fields, dates, and payment method values.
- `FR-003` - Backend sync conflict detection must be reliable for customer updates, sale updates, sale item changes, and abono updates.
- `FR-004` - Backend sync handlers must fail, retry, or dead-letter invalid operations explicitly instead of silently succeeding on missing rows, version mismatches, or invalid parents.
- `FR-005` - Compound sale operations must be locally atomic enough to avoid partial `sales`/`sale_items` state and partial sync queue state when an error occurs.
- `FR-006` - Compound offline operations must carry grouping or correlation metadata so sale headers, sale items, and related abonos can be ordered, debugged, and retried coherently.
- `FR-007` - Cobros/abonos hooks and UI must use local offline services and allow the core create/update/delete lifecycle to be tested.
- `FR-008` - Balances shown in customer detail, sale detail, and cobros must have a clear source of truth and remain consistent after offline abono creation and sync.
- `FR-009` - The migration must include a real validation path for offline create customer + sale + sale items + abono, reconnect, push, pull, and verify on a fresh client.

## Non-Functional Requirements

- `NFR-001` - Preserve Avileo multi-tenancy rules: backend repository and sync writes must filter by `ctx.businessId` or equivalent tenant guarantees.
- `NFR-002` - Preserve offline-first behavior: core vendor write flows must not require network access.
- `NFR-003` - Preserve generated-file ownership: generated frontend sync files must be regenerated, not hand-edited.
- `NFR-004` - Keep changes minimal and compatibility-aware; do not introduce aliases or backward-compatibility paths unless persisted data or clients require them.
- `NFR-005` - Validation must include typecheck/build and targeted unit/integration/E2E tests for the migrated flow.
- `NFR-006` - User-facing text introduced in UI tasks must remain Spanish for Peru locale.

## Acceptance Criteria

- `useEngineService("payments")` no longer appears in app flow code; payment/cobro flows use the canonical service key.
- Schema parity checks pass for `customers`, `sales`, `sale_items`, and `abonos` across shared, backend, generated frontend, and sync payload definitions.
- Customer updates, abono updates, sale updates, and sale item changes increment or compare versions consistently with conflict resolvers.
- Sale creation with items and delivery finalization do not leave partial local state or orphan sync operations if an intermediate step fails.
- Sync operations generated by the app match the backend `/sync/batch` contract, including canonical entity names and local version fields.
- A gold-path offline test demonstrates customer + credit sale + sale items + abono while offline, reconnect/push, pull on a clean/fresh client, and balance verification.
- `bun run sync:validate`, package typechecks, targeted backend tests, and targeted app/E2E tests pass or have documented environment blockers.

## Constraints

- The plan must not modify application source during planning.
- Backend service/repository methods must keep `RequestContext` as the first parameter.
- Frontend generated files under `packages/app/app/lib/sync/generated/` must be regenerated through `bun run sync:generate` after generator/schema changes.
- Offline proof image upload is optional for the core migration unless explicitly included in task execution.
- Existing user changes in the worktree must not be reverted during execution.

## Open Questions

- Should `saldo` be accepted as a cobro/abono payment method, or should it remain refund-only?
- Should `tarjeta` be kept in cobros UI and sync payloads?
- Should operation grouping use the existing backend `correlationId`, a local `syncGroupId`, or both with a clear mapping?
- Should the final E2E run against real backend/database, MSW with exact backend contract, or a two-tier approach?
