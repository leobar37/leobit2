# Context: Migrate to Generated Services

## Overview

Migrate Avileo's frontend service layer from manual service classes to auto-generated services from `@avileo/drizzle-sync`, extended with custom business logic. This eliminates redundancy between `registerAppServices` and the `entities` array in `createAvileoSyncEngine`, removes 111 repetitive `engine.use()` calls across hooks, and establishes `useEngineService<T>()` as the canonical way to access services.

## Background

Currently, Avileo has **two parallel service systems**:

1. **Generated services** (`packages/app/app/lib/sync/generated/services.ts`) — Auto-generated by `drizzle-sync` with basic CRUD (`findById`, `list`, `create`, `update`, `delete`)
2. **Manual services** (`packages/app/app/lib/services/*.ts`) — Hand-written classes extending the generated ones with custom business logic (search, pagination, atomic multi-entity operations, aggregations)

The generated services are registered in `createAvileoSyncEngine.entities[]`, but the manual services are registered separately via `registerAppServices(engine)` using `engine.use()`. Hooks then call `engine.use()` 111 times to get service instances.

This dual system is redundant and confusing. The goal is to unify everything so that:
- Services are defined **once** in `entities[]`
- Hooks access them via `useEngineService<T>("name")`
- Custom business logic lives in **extension classes** that inherit from generated services

## Goal

1. Fix the `drizzle-sync` type system so that `EntityServiceDefinition.factory` receives the full `SyncClientEngine` instance (which implements `SyncClientEngineLike`) instead of an incompatible `SyncClientEngineContext`
2. Regenerate services so they work correctly when instantiated by the engine
3. Extend generated services with custom methods from manual services
4. Update `createAvileoSyncEngine` to use extended service classes
5. Eliminate `registerAppServices.ts`
6. Migrate all hooks to `useEngineService<T>()`
7. Pass TypeScript type checking and existing tests

## Key Decisions

- **Option A chosen**: Fix the generator in `drizzle-sync` rather than work around it
- **Services will be extended, not replaced**: Manual services contain ~100 custom methods with business logic that cannot be auto-generated (atomic sales+items, tag assignment, group management, etc.)
- **CRUD methods in manual services will be removed**: Once extending the generated class, manual overrides of `create`, `update`, `delete`, `findById`, `list` become redundant

## Scope Boundaries

- **In scope**: `packages/drizzle-sync/src/`, `packages/app/app/lib/services/`, `packages/app/app/hooks/`, `packages/app/app/lib/sync/`
- **Out of scope**: Backend changes, database schema changes, UI components (unless they import service types), E2E test changes
- **Not modifying**: The service generator's output format (same methods generated), only the factory parameter type changes
